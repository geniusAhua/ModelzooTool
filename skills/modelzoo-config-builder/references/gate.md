# 开工前门禁与用户输入

> 由 `SKILL.md` 按需加载。**每次动手前 30 秒过一遍，不得跳过、不得自行拍板。**

## 0. 开工前门禁（每次动手前 30 秒过一遍）

> 按「先问平台 → 定形态 → 定复杂度 → 定细节」排序，**不得跳过、不得自行拍板**。
> 一句话记住：**先问清「哪个平台、谁的脚本、在哪跑、谁执行、容器叫什么」，再写最简的一版；不验证，先交模板。**
> ⚠️ **host / container 与平台无关**：任何平台都是 host 出 2 个脚本、container 出 1 个（见 §0-B）。

### A. 先分清脚本是谁（client / server / 框架）

| 脚本 | 职责 | 典型内容 |
|------|------|----------|
| **server 脚本** | 只负责起推理服务 | 一条 `vllm serve ...`（+ 少量变量） |
| **client 脚本** | 只负责压测 / 精度评测 / 抓数据 | 一条 `lm_eval ...` / `bench serve ...` |
| **框架脚本** | 只负责「准备容器 + 在容器里启动 ModelzooTool」 | `docker run` / `docker exec` + `main.py --config ... --task ...` |

- 用户说「写个脚本」却**没说清是 client 还是 server** → **必须先问**，不要猜、不要一次给两个。
- 识别线索：`serve` / `launch_server` / `ray start` → server；`bench` / `lm_eval` / `python xxx_test.py` → client；`docker run` / `main.py` → 框架。

#### A-0 先问：到底要不要单独写脚本？

| 情况 | 做法 |
|------|------|
| 用户**没要求**一个可单独执行的脚本 | **不创建**：把命令直接写进 config 的 `server.cmd` / `client.cmd`，由工具原样执行 |
| 用户**明确要求**独立脚本（多步准备、多人复用、要单独交付） | 才创建一个（同时受 A-1 / A-2 约束） |

- **必须先问，不得默认生成**。多一个脚本 = 多一层间接：日志里只剩 `run: bash xxx.sh`，看不到真实命令。
- 能不建就不建：config 里一条 `cmd` 最直接，`--dry-run` 也能直接渲染出来。

#### A-1 server / client 脚本：三条硬性约束

| # | 约束 |
|---|------|
| 1 | **一个脚本只服务一个具体任务**：脚本名、命令、参数全部钉死；**不得做参数化**（不解析 `$1`、不收 `--port` / `--bs`、不留「可选配置」），**用户明确要求才加** |
| 2 | **不做兼容适配**：不判厂商 / 不判镜像版本 / 不写 if-else 分支、不探测依赖是否安装、不做 fallback；目标机器是什么就写什么 |
| 3 | **代码量最小优先**：能一行 `exec` 就一行；非必要代码（大段注释、彩色输出、时间戳、日志轮转、防御性检查）一律不加 |

> 与框架脚本相反：框架脚本**必须**透传 `--task/--tag/--dry-run` 等 CLI（[delivery.md](./delivery.md) §4.1），
> server / client 脚本则**不传参、不接收参数**。

#### A-2 建了脚本就必须打印「最终执行的命令」（硬性）

ModelzooTool 的 server/client 日志开头只记 `run: <config 里的 cmd>`（`bin/core/modelzooProcessor.py:87`）。
若 cmd 是 `bash client.sh`，日志里就**看不到脚本内部真正执行的命令**。因此脚本必须自己把它打出来：

| 要求 | 做法 |
|------|------|
| 打印时机 | **在执行前**（`exec` 之后就换进程了，再打也没意义） |
| 打印方式 | 推荐 `set -x`（trace 走 stderr，工具已 `stderr=STDOUT` 合并进日志，`modelzooProcessor.py:41`）；或 `echo "+ <最终命令>"` |
| 打印内容 | **变量已展开的真实命令**，可直接复制重跑；不要打成 `$FOO` 原样 |
| 验收 | client 日志里能直接搜到那行命令（不依赖任何额外开关） |

### B. 再分清脚本在哪跑（host / container）——**与平台无关，全平台同一规则**

| 运行位置 | 需要几个脚本 | 说明 |
|----------|-------------|------|
| **container 内** | **只做一个** | 不用考虑创建容器 / 设备挂载 / 镜像 / 容器名；容器已存在，脚本只需把那条命令拉起来。**就是 host 形态的第 ② 个脚本**，可复用 |
| **host（宿主机）** | **必须两个，且分两步**：① 启动容器的脚本；② 进容器后真正跑命令的脚本 | **宿主机不得执行应当在容器内执行的操作**（如 `vllm serve` / `lm_eval`）。**不要合并成一个**：分开后，只有容器可用（容器已存在 / 别人起的）时可以**直接复用第 ② 个** |

- **必须问用户**：「这个脚本跑在宿主机还是容器里？」问不清就写明假设（host 两个 / container 一个）让用户确认。
- **host 形态还必须问：用哪个镜像（IMAGE）？** 镜像跟模型/框架/厂商绑定（沐曦还要带对应 vllm_metax 版本），拿不到镜像名就先不写死、做成变量。
- 平台（NVIDIA / MetaX）只影响「起容器的参数」，**不改变脚本个数**：宿主机上 NVIDIA 也要 `run_nvidia.sh`+`run_in_container_nvidia.sh` 两个，MetaX 也要 `run_metax.sh`+`run_in_container_metax.sh` 两个；容器内形态两家都只写一个。

### C. 脚本越简单越好（硬性：代码量最小优先）

- 目的只有一个：**启动 ModelzooTool**（框架脚本）或**执行那条 server/client 命令**（server/client 脚本）。
- **代码量最小优先**：先写最短能跑通的版本，不得为「以后可能用到」预留变量 / 函数 / 分支。
- **不做兼容适配**：不按厂商 / 版本分支、不探测依赖、不做 fallback（server/client 脚本尤其如此，见 §0-A）。
- 默认**不**加：结果解析、汇总表格、失败重试、超时轮询、日志轮转、参数解析器、多任务编排、进度条、彩色输出。
- 用户明确要才加；能一行 `exec` 解决的不要写 20 行 `if`。

### D. 执行用户 / uid：只归框架脚本，且必须问

- **client / server 脚本里不写**任何 `useradd` / `su` / `id -u` / uid 判断 —— 那是框架脚本的职责。
- 框架脚本里**必须问**：执行用户 `user`、`uid`（以及要不要补 `video,root` 组），并给建议默认值。
- 框架脚本用 `useradd -m -l -u <uid>` + `su - <user>`（[delivery.md](./delivery.md) §4.2）；client/server 脚本只管被调用。

### E. 配置里的环境变量：进 `env`，不进 `cmd`

| 情况 | 做法 |
|------|------|
| 固定环境变量（`MACA_*`、`HF_ENDPOINT`、`CUDA_*` …） | 写进 config 的 `server.env` / `client.env`（任务级覆盖顶层） |
| **容易变的值**（端口、并发、条数、fewshot、输出路径） | **框架脚本**：做成顶部变量或 CLI 参数；**server/client 脚本**：**直接写死**（一个脚本一个任务，不传参，见 §0-A） |
| 需要随 case 变的值 | 用 `{bs}` / `{input}` / `{output}` / `{port}` 等魔法变量 |

- 禁止 `FOO=1 bash xxx.sh` 这种把 env 塞进 `cmd` 的写法（难检索、与 `env` 重复、任务级覆盖关系看不清）。

### F. 交付节奏：先模板，不验证，用户检查后再定要不要验

- **先交付一版最简模板**，默认**不做任何验证**（不装依赖、不起容器、不跑任务、不做 dry-run）。
- 交付后**由用户先检查**；用户认为需要验证时，再按 [validation.md](./validation.md) 做，且**只做用户点名的那几项**。
- 不做「预防性」的复杂校验（目录检查、重试、锁、进度条）。潜在问题**先问用户**，并给出你的建议。
- 交付时用一句话说明「哪些是假定、哪些需要用户确认」，方便后续迭代。

### G. 容器名必须带工号后缀（host 形态硬性要求）

宿主机形态会真实 `docker run`，容器落在共享机器上，**名字必须带工号**，否则会撞掉别人的容器。

| 规则 | 做法 |
|------|------|
| 命名格式 | `<基础名>-<工号>`，例：`mz-run-m01088` |
| 工号来源 | **就是执行用户的工号/用户名**（如 `m01088`）。在脚本顶部做成变量（如 `USER_SUFFIX="m01088"`），**生成时必须问用户** |
| 禁止 | ① 裸名（`modelzoo` / `vllm` / `test`）—— 共享机器上必撞；② 用 `$(id -un)` 自己猜（容器可能由别人代起、工号不等于登录名）；③ 留空或保留 `<工号>` 占位符就跑 |
| 清理/保留 | `--keep`、`docker rm -f` **只能针对这个带后缀的名字**，禁止 `docker rm -f $(docker ps -q ...)` 之类通配清理（会误删别人的容器） |

> 模板已内置：`USER_SUFFIX` + `CONTAINER="${CONTAINER:-mz-run-${USER_SUFFIX}}"` + 未填即报错，
> 见 [run_host_template.sh](./run_host_template.sh)。

## 0.1 用户输入（只问这三样）

| 输入 | 说明 | 去哪 |
|------|------|------|
| server 命令 | 启动推理服务的那条命令 | 默认 `server.cmd`（或任务级 `cmd`） |
| client 命令 | 打流/压测/测量脚本命令 | 默认 `client.cmd`（或任务级 `cmd`） |
| 环境变量 | server / client 各自需要 export 的变量 | `server.env` / `client.env` |

如果用户已经给了这三样，**不要重新索要整份配置**，直接进入推导。
